1. Why these files exist at all

Before Phase 7, this project ran as two completely different kinds of things, glued together only by shared knowledge of ports and hostnames. The four Spring Boot services — order-service, inventory-service, payment-service, search-indexer-service — ran as host processes, started with ./gradlew :order-service:bootRun (and the equivalent for each other module) directly on the developer's machine. Every piece of infrastructure they depended on — three Postgres databases, Redis, Kafka, Elasticsearch, Kibana, Logstash, Filebeat, Prometheus, Grafana, Kafka UI — ran as a Docker container, but each one started by its own individual, one-off docker run command, typed by hand, existing nowhere as a reviewable file.

That second half was the real liability. Nothing in the repository said what image version each infra piece used, what environment variables it needed, what ports it published, or what order things had to start in. This actually bit the project directly: earlier in this same effort, fixing a Logstash index-naming bug required manually running docker rm -f order-logstash and then manually re-typing the same docker run command from memory to pick up a config change — a workflow that only works as long as whoever's doing it remembers the exact flags, and that leaves zero trace in git of what was actually running. A second developer pulling this repo fresh would have no way to reconstruct the same environment without asking someone.

Containerizing the four Spring Boot services and writing docker-compose.yml solves three separate problems at once:

  • Reproducibility. The entire 15-container system — every infra piece and every app service — is now declared in one file. docker compose up -d --build from a clean checkout reconstructs it exactly, with no tribal knowledge required.
  • Environment parity. Once order-service runs inside eclipse-temurin:21-jre, it no longer matters what JDK version (or whether any JDK at all) is installed on the host machine running it. The image carries its own runtime.
  • It's the direct prerequisite for Phase 8. Kubernetes deploys container images — it has no concept of "SSH into a box and run gradlew bootRun." Without a real, standalone, runnable image for each service, there is nothing for a future Kubernetes Deployment's image: field to point at. This is covered in depth in §5.

Concretely, the shift also changes how each service reaches its dependencies. Before Phase 7, order-service (a host process) talked to Postgres via localhost:5432 — that address is order-service's own machine's loopback interface, reachable only because Postgres's container published port 5432 to that same host. After Phase 7, order-service is itself a container on the same Docker network as order-postgres, and it addresses it by container name — order-postgres:5432 — never touching localhost at all. This is exactly what the project's application-docker.yml profile files (added in the step before this one) exist to express, and it's covered in detail in §3.

2. The Dockerfile, line by line

All four Dockerfiles are structurally identical — same two stages, same base images, same instruction order — differing only in the module name, the copied src/ directory, and the EXPOSEd port. order-service/Dockerfile is used as the walkthrough; differences in the other three are called out where they occur.

order-service/Dockerfile
# Build context MUST be the repo root (order-platform), not this module's
# own directory — e.g. from the repo root:
#   docker build -f order-service/Dockerfile -t order-service .
# This is a multi-module Gradle build: settings.gradle declares all four
# subprojects, and Gradle's configuration phase evaluates every declared
# subproject's build.gradle even when only one subproject's task is
# requested (":order-service:bootJar" below) — so gradlew, the root
# settings.gradle/build.gradle, and every subproject's own build.gradle need
# to be present in the build context, not just this module's own files.
# Only order-service's actual src/ is copied, though: this project's
# no-shared-module architecture means no subproject's compileJava/bootJar
# task ever reads another subproject's source.

FROM eclipse-temurin:21-jdk AS build
WORKDIR /workspace

COPY gradlew .
COPY gradle gradle
COPY settings.gradle build.gradle ./
COPY order-service/build.gradle order-service/build.gradle
COPY inventory-service/build.gradle inventory-service/build.gradle
COPY payment-service/build.gradle payment-service/build.gradle
COPY search-indexer-service/build.gradle search-indexer-service/build.gradle
COPY order-service/src order-service/src

RUN chmod +x gradlew && ./gradlew :order-service:bootJar --no-daemon

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /workspace/order-service/build/libs/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Why a multi-stage build

FROM eclipse-temurin:21-jdk AS build starts the first stage, named build, on a full JDK image — javac, jshell, the whole toolchain. FROM eclipse-temurin:21-jre (no AS, so this becomes the final stage) starts completely fresh on a JRE-only image — no compiler, no build tools, nothing that isn't needed to actually run a compiled jar. Only one instruction bridges the two: COPY --from=build ... *.jar app.jar, which reaches back into the build stage's filesystem and pulls across exactly one file.

Everything else stage 1 produced or downloaded — the JDK itself, the Gradle wrapper's downloaded distribution, the full Maven-Central dependency cache under ~/.gradle, the entire order-service/src tree, every intermediate .class file — is simply never referenced by the final image, so it's discarded along with the rest of the build stage's layers. Without the second stage — if this Dockerfile were a single FROM eclipse-temurin:21-jdk build that just ran the app in place — every one of those things would ship inside the running container: a compiler and full build toolchain sitting inside a production process is dead weight (larger image, slower pulls, slower container starts) and a larger attack surface for no operational benefit, since none of it is ever touched again after the jar exists.

Why the build context has to be the repo root

This is mechanical, not stylistic. settings.gradle at the repo root declares:

include 'order-service', 'inventory-service', 'payment-service', 'search-indexer-service'

Gradle's configuration phase evaluates every declared subproject's build.gradle before it can run any task — including a task scoped to just one subproject, like :order-service:bootJar. It has to: resolving the project graph and any inter-project dependency wiring requires knowing what every subproject declares, even ones the requested task never touches. So the build stage needs gradlew, the gradle/ wrapper directory, the root settings.gradle/build.gradle, and all four subprojects' own build.gradle files present — not just order-service's.

What it does not need is the other three subprojects' actual Java source. Because this project deliberately has no shared schema/utility module (every service keeps its own local copy of the Kafka event classes it depends on), no subproject's compileJava ever reads another subproject's src/ — so only COPY order-service/src order-service/src is needed, not the sibling src/ trees.

What breaks without it Running docker build -f order-service/Dockerfile order-service/ — treating the module's own folder as the build context — fails immediately at the very first COPY gradlew . instruction: from inside order-service/, there is no gradlew, no settings.gradle, no sibling build.gradle files to copy. The context simply doesn't contain them.

COPY ordering and Docker's layer cache

Docker caches each instruction as its own layer, keyed by the instruction plus a hash of whatever files it copies in. If an earlier layer's inputs change, every layer after it is invalidated and re-run, even if that later layer's own inputs are unchanged — Docker has no way to know a later step doesn't depend on an earlier one without re-executing it. The classic justification for "copy dependency-related files before source" is that it lets a separate dependency-priming step stay cached across source-only changes.

Worth knowing for the follow-up question In this exact Dockerfile, that optimization isn't fully realized yet. There is only one RUN in the build stage — RUN chmod +x gradlew && ./gradlew :order-service:bootJar --no-daemon — and it comes after the src COPY, not before a separate dependency-resolution step. Since order-service/src changes on nearly every commit, that one RUN layer's cache is invalidated on nearly every build, meaning Gradle re-downloads its full dependency set from Maven Central inside the build stage almost every time, rather than reusing a previously-resolved cache. The COPY ordering (gradlew → wrapper → settings/build.gradle files → src) still separates "rarely changes" from "changes constantly" at the layer level, which is the right shape to build on — but realizing the caching win fully would mean adding something like RUN ./gradlew :order-service:dependencies --no-daemon between the build.gradle COPYs and the src COPY (or switching to a BuildKit cache mount, RUN --mount=type=cache,target=/root/.gradle), neither of which this Dockerfile does today. A sharp reviewer will ask about this — the honest answer is "the ordering is set up for it, but the priming step itself isn't there yet."

WORKDIR and where relative paths resolve

WORKDIR /workspace in the build stage sets the base directory for every subsequent relative COPY/RUN in that stage. WORKDIR /app in the final stage does the same for the runtime image — and critically, it also becomes the JVM process's actual current working directory when ENTRYPOINT ["java", "-jar", "app.jar"] executes, since nothing changes it afterward.

This isn't incidental. logback-spring.xml (added in an earlier increment of this project) configures a file appender with a relative path:

<file>logs/order-service.log</file>

Relative to what, at runtime? Relative to the JVM's working directory — /app, because of this WORKDIR instruction. So the log file actually lands at /app/logs/order-service.log inside the container. That path is exactly what docker-compose.yml's volume mount targets for this service: order-service-logs:/app/logs.

What breaks without it If WORKDIR /app were missing (or set to something else), the log file would be written somewhere else entirely — and the Filebeat container, which mounts the same named volume read-only at /logs/order-service, would find an empty directory. No parse errors, no crash — just silence. Nothing would ever reach Logstash or Elasticsearch, and there'd be no obvious error message pointing at why, exactly the kind of quiet, hard-to-diagnose failure this project already hit once with the Logstash index-naming issue.

What EXPOSE actually does — and doesn't

EXPOSE 8080 is documentation baked into the image metadata. It does not publish the port to the host, and it does not restrict or configure what port the process inside the container actually listens on — Spring Boot binds to 8080 because server.port: 8080 in application.yaml says so, completely independent of this line. What actually makes port 8080 reachable from the host is docker-compose.yml's explicit ports: - "8080:8080" mapping for this service — covered in §3. The one real functional effect EXPOSE has is with docker run -P (publish-all), which uses EXPOSEd ports to decide what to auto-map to random host ports — a convenience this project doesn't rely on, since Compose's explicit port mappings are used instead.

Why ENTRYPOINT, and why this exact form

ENTRYPOINT ["java", "-jar", "app.jar"]

This is exec form — a JSON array — not shell form (ENTRYPOINT java -jar app.jar as a bare string). The difference matters: exec form runs java directly as the container's PID 1, with no intermediate shell in between. Shell form would instead run /bin/sh -c "java -jar app.jar", making the shell PID 1 and java its child — and a very common, very real Docker failure mode is that docker stop sends SIGTERM to PID 1, which a shell frequently does not forward to its child process, so the JVM never gets the signal to shut down gracefully and the container hangs until Docker's hard-kill timeout expires. Exec form avoids that entirely by giving the JVM the signal directly.

ENTRYPOINT (rather than CMD) is the right choice here specifically because there's exactly one way this image is ever meant to run — always launch this one jar. CMD is the idiom for a default that's meant to be easily overridden at docker run time; this project doesn't need that, since environment-specific behavior (the docker Spring profile) is switched via an environment variable — SPRING_PROFILES_ACTIVE=docker, set in docker-compose.yml — not via a different launch command.

3. docker-compose.yml, section by section

The problem this file solves is the one described in §1: a set of individually-typed docker run commands has no single source of truth, no version history, and no way to reconstruct the whole system in one step. docker-compose.yml replaces all of that with one declarative file, checked into git, describing every container's image, configuration, storage, health, and startup dependencies — reproducible with a single docker compose up -d --build.

Anatomy of a service definition: order-postgres

  order-postgres:
    image: postgres:16
    container_name: order-postgres
    environment:
      POSTGRES_DB: orders
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
    ports:
      - "5432:5432"
    volumes:
      - postgres-order-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 10
    networks:
      - order-platform-net
KeyWhat it does
imagePulls the official postgres:16 image. Pinning the major version — not postgres:latest — means a future rebuild won't silently jump to Postgres 17 and change on-disk format compatibility or behavior underneath the project.
container_nameWithout it, Compose auto-generates a name like order-service-order-postgres-1 (project + service + replica index). The explicit name here is exactly what makes jdbc:postgresql://order-postgres:5432/orders resolvable from other containers — Docker runs an embedded DNS server on every user-defined bridge network that resolves container names to their internal IPs.
environmentThese three variables are read by the official Postgres image's own entrypoint script on first boot (when the data directory is empty) to auto-create the database, user, and password. They match what order-service's own spring.datasource.username: ${DB_USERNAME:postgres} default expects.
ports"5432:5432" (host:container) only matters for reaching Postgres from the host machine — a local psql, a GUI client. Containers on order-platform-net never use this mapping; they talk to the container's internal port 5432 directly over the Docker network, regardless of what's published to the host.
volumesA named volume, postgres-order-data, mounted at Postgres's real data directory. See the dedicated discussion below — this is what makes the data survive a container being removed and recreated.
healthcheckRuns pg_isready -U postgres (a lightweight CLI bundled in the image whose only job is "can this server accept a connection") every 5 seconds, up to 10 tries. This is what gives depends_on: condition: service_healthy anything meaningful to wait on — covered below with a concrete failure scenario.
networksPuts the container on the shared order-platform-net bridge network — the source of both the name-based DNS resolution above and isolation from anything not on this network.

Why Kafka's environment block is shaped the way it is: two listeners

      KAFKA_LISTENERS: PLAINTEXT://:29092,PLAINTEXT_HOST://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://order-kafka:29092,PLAINTEXT_HOST://localhost:9092
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT,PLAINTEXT_HOST:PLAINTEXT
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT

(Alongside KAFKA_PROCESS_ROLES: broker,controller and KAFKA_NODE_ID: 1 — this is a single node acting as both broker and KRaft controller, Kafka's newer Zookeeper-free consensus mode, with itself as the sole quorum voter via KAFKA_CONTROLLER_QUORUM_VOTERS: 1@localhost:9093.)

The Kafka wire protocol isn't a simple "connect once, keep talking to the same socket" protocol like plain HTTP. A client's very first connection to any broker (the "bootstrap" broker) returns a metadata response telling the client the actual host:port to use for every partition leader it will talk to next — and the client switches to whatever address that response advertises. That means the address a broker advertises has to actually be reachable from wherever the client lives.

This project has two genuinely different populations of Kafka clients: the four app services, which are other containers on order-platform-net and resolve order-kafka via Docker's internal DNS; and host-side tools — a locally-run kafka-consumer-groups.sh, exactly like the ones used earlier in this project to reset search-indexer-service's consumer offsets — for which order-kafka means nothing (it isn't a real DNS name outside the Docker network) and only localhost:9092, published via ports: "9092:9092", works.

What goes wrong with only one listener If Kafka advertised only order-kafka:29092, a host-side client connecting via localhost:9092 would complete its first handshake fine — the port is published — but the very next request would come back telling it to now talk to order-kafka:29092, which the host can't resolve. Every request after the first would then fail to connect, while the initial connection looked completely healthy. This is a well-known, very real "Kafka in Docker" failure mode, and it's exactly why two separate listener names exist here — PLAINTEXT (internal, :29092) and PLAINTEXT_HOST (host-facing, :9092) — each advertised with the address appropriate to whoever's actually resolving it. It's also exactly why this project's application-docker.yml files point at order-kafka:29092 while the plain application.yml (used by host-based bootRun) still says localhost:9092 — they're each using the listener meant for them.

KAFKA_LISTENER_SECURITY_PROTOCOL_MAP maps each listener name to a security protocol — all three are PLAINTEXT here (no TLS, no SASL — appropriate for local dev, not anything resembling production). KAFKA_INTER_BROKER_LISTENER_NAME tells brokers which listener to use when talking to each other (moot with a single broker, but still required configuration). KAFKA_CONTROLLER_LISTENER_NAMES keeps KRaft's own consensus traffic on its own listener (port 9093), separate from client data traffic — control-plane kept apart from data-plane on principle.

healthcheck and depends_on: condition — what it actually enforces

  order-service:
    ...
    depends_on:
      order-postgres:
        condition: service_healthy
      order-kafka:
        condition: service_healthy
      order-redis:
        condition: service_started

A plain depends_on with no condition — the form actually used for order-redis here, and for order-prometheus/order-logstash elsewhere in this file — only orders container starts. Compose launches the dependency's process and, the moment it exists, considers the dependency satisfied and proceeds to start whatever depends on it — regardless of whether that process has actually finished initializing.

Concrete failure scenario, specific to this project order-service runs Flyway migrations at startup, before Hibernate even initializes (spring.flyway.enabled: true, spring.jpa.hibernate.ddl-auto: validate — Flyway owns the schema, Hibernate only validates against it, a decision already made earlier in this project). Flyway has to successfully open a JDBC connection and run its migration SQL against order-postgres before order-service's application context can finish starting at all. Postgres's own startup — especially against a brand-new, empty volume — involves starting the postmaster process, running initdb, creating the configured database/user/password, and then finally opening its listening socket. That sequence takes real, measurable time. If depends_on: order-postgres had no condition, order-service's container (and its Flyway connection attempt) could start executing while Postgres is still mid-initdb, not yet accepting connections at all — producing a connection-refused failure, and depending on how much retry/backoff HikariCP's pool initialization tolerates, either a flaky slow startup or an outright failed one. This is a classic, very real "works most of the time, fails under load or on a cold machine" bug in exactly this kind of multi-container system.

condition: service_healthy closes that gap by tying the dependency gate to the healthcheck's actual result, not merely "the process exists." Compose won't start order-service's container until pg_isready -U postgres has genuinely returned success against order-postgres — a real, polled, deterministic readiness signal, not a guess.

Worth noting honestly: order-redis is depended on with condition: service_started, not service_healthy — because order-redis's own service definition has no healthcheck block at all in this file, so service_healthy isn't even a condition Compose could evaluate for it. In practice this is a smaller real risk than the Postgres/Kafka cases — Redis starts almost instantly with no schema/migration step, and nothing in these services' startup paths does an eager, blocking connectivity check against Redis the way Flyway does against Postgres — but it is a genuinely weaker guarantee than its siblings get, and it's exactly the kind of gap a sharp reviewer would ask about.

Named volumes vs. bind mounts

Both mechanisms attach external storage to a container, but for opposite reasons here.

Named volumes — data the running system generates and owns

postgres-order-data, postgres-inventory-data, postgres-payment-data, elasticsearch-data, prometheus-data, grafana-data, and the four per-service log volumes (order-service-logs, etc.) are all named volumes: Postgres's actual table rows, Elasticsearch's index segments, Prometheus's TSDB chunks, Grafana's own dashboard/user database, and each service's log output. Docker manages the real storage location itself, under Docker's own data root — not somewhere meant to be browsed directly. The load-bearing property is that a named volume's lifecycle is decoupled from any specific container: removing and recreating a container (exactly what docker compose up --build did to every infra container in the previous step of this project) leaves the volume untouched. Only an explicit docker compose down -v, or a direct docker volume rm, destroys it. Without named volumes, the data would live in the container's own writable layer and vanish the instant that specific container is removed — which is precisely why the fresh containers from the last docker compose up -d --build run started with an empty orders table: they were the very first containers ever attached to those particular named volumes, not a reattachment to whatever storage the earlier, manually-run containers happened to use.

Bind mounts — config files owned by the repo

      - ./infra/logstash/logstash.conf:/usr/share/logstash/pipeline/logstash.conf
      - ./infra/filebeat/filebeat.yml:/usr/share/filebeat/filebeat.yml:ro
      - ./infra/prometheus/prometheus.yml:/etc/prometheus/prometheus.yml

These map a real path on the host filesystem — files that live in this repo, under version control, editable in a normal text editor — directly into the container. The intent is the opposite of a named volume: the file's content is authored and owned outside the container, and the container just reads whatever is currently on disk. This is exactly the workflow used a few steps ago in this project, when fixing Logstash's index-naming bug meant editing infra/logstash/logstash.conf in the repo and recreating the order-logstash container — no image rebuild needed, because the file was never baked into a layer in the first place. The :ro suffix on Filebeat's mounts (read-only) is a small extra safety measure: Filebeat has no legitimate reason to ever write to its own config, so a bug or compromise there can't corrupt the source-of-truth file sitting in the repo.

One overlap worth naming: the four per-service log directories are named volumes, not bind mounts, even though a human might reasonably want to tail them directly. That's because they're written by one container (the app service) and read by another (Filebeat) — a volume shared between two containers, not between a container and the host repo. A bind mount to a host directory would also have worked here, and would arguably be more convenient for direct host-side log inspection — but the named-volume choice avoids depending on a specific host directory layout existing, which keeps the compose file portable across different developer machines or CI runners. It's a real trade-off, not a hard rule.

networks: one shared network instead of a patchwork

networks:
  order-platform-net:
    driver: bridge

Every one of the 15 services declares networks: - order-platform-net, putting all of them on one shared, user-defined bridge network. This replaces what the earlier, hand-run-container era of this project effectively had instead: separate ad-hoc networks created by whatever docker run --network ... flags someone happened to type, with containers on different networks unable to resolve each other by name at all — forcing exactly the kind of host.docker.internal workaround Prometheus's scrape config used before it was fixed to point at order-service:8080 directly. One shared network means every container gets the same embedded DNS resolution of every other container's name, with no cross-network routing tricks needed — and, because it's a distinct user-defined network rather than Docker's default bridge, anything not explicitly attached to order-platform-net can't resolve or reach these containers by name at all, which is a meaningful isolation boundary, not just a naming convenience.

volumes: the bottom-level declarations

volumes:
  postgres-order-data:
  postgres-inventory-data:
  postgres-payment-data:
  elasticsearch-data:
  prometheus-data:
  grafana-data:
  order-service-logs:
  inventory-service-logs:
  payment-service-logs:
  search-indexer-service-logs:

Each bare name under the top-level volumes: key, with no further config (no driver_opts, no external: true), tells Compose to create a standard, locally-managed Docker volume the first time it's needed, and to keep reusing that same volume on every subsequent docker compose up — for as long as it isn't explicitly torn down.

Not shown as an edge because it isn't a network call: Filebeat's actual log sources are the four per-service named volumes (order-service-logs etc.), shared read-only with the app containers that write them — see §3. search-indexer-service has no edge from Prometheus, since it was never given the Actuator dependency (§2). All Kafka traffic uses the internal PLAINTEXT listener on :29092, not the host-facing :9092 listener — every one of these clients is itself a container.

5. What we actually achieved

The headline benefit is reproducibility: docker compose up -d --build, run from a clean checkout of this repository, reconstructs the entire 15-container system — three databases, Redis, Kafka, the whole Elastic logging stack, Prometheus and Grafana, and all four application services, built from source — deterministically, with no manually-typed docker run commands to remember, and no risk of two developers' environments quietly drifting apart. Onboarding a new engineer now requires Docker and this repository — not a specific locally-installed JDK version, not a manually set-up Postgres/Kafka/Elasticsearch, not tribal knowledge of which flags some earlier docker run invocation used.

More specifically, this stage is what makes Phase 8 (Kubernetes) possible at all. Kubernetes's fundamental unit of deployment is a container image referenced in a Pod spec's image: field — it has no mechanism for "SSH into a host and run gradlew bootRun." Every Kubernetes primitive that matters for this project going forward — a Deployment managing replicas of order-service, a Service load-balancing across them, a rolling update replacing old Pods with new ones — presupposes that "order-service" already means a real, standalone, runnable image that can be pulled and started without any of this repository's source code or build tooling present. That's exactly what order-service/Dockerfile now produces, and what was confirmed working end-to-end when the full stack was built and started via Compose in this same project.

What this stage deliberately does not solve yet

Worth naming honestly, since these are exactly the questions a good interviewer follows up with:

  • No image registry. The four app images exist only in the local Docker image store on whichever machine built them (tagged order-service-order-service:latest etc. by Compose's own default naming). There's no push to a registry, and no tagging strategy beyond the implicit :latest — nothing yet distinguishes "the image currently running" from "the image the current source would produce."
  • Single instance, no replicas. Every service in docker-compose.yml runs as exactly one container. There's no load balancing, no redundancy, no rolling-update story — all of that is what Phase 8 exists to add.
  • Credentials in plaintext environment variables. POSTGRES_PASSWORD: postgres and friends are fine for local development, but they're sitting in a checked-in YAML file — nothing here is what a real secrets-management story would look like.
  • The Gradle dependency-cache optimization noted in §2 isn't realized yet — every image rebuild currently re-downloads the full dependency set rather than reusing a cached layer.
