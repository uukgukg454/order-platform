1. Helm templating fundamentals

A Helm chart is a directory with a specific shape. helm/order-platform/ has all three required pieces: Chart.yaml (chart metadata — name, version), values.yaml (the default configuration data every template reads from), and templates/ (files that mix literal YAML with Go template directives, rendered against those values to produce real Kubernetes manifests).

helm/order-platform/Chart.yaml
apiVersion: v2
name: order-platform
description: Helm chart for the order-platform app services (order-service, inventory-service, payment-service, search-indexer-service)
type: application
version: 0.1.0
appVersion: "1.0.0"

values.yaml supplies the data structure every template accesses as .Values — in this chart, three top-level keys: common (settings shared by every service), services (a map keyed by service name, holding what differs per service — the subject of §3), and ingress (the routing config added afterward). Nothing in a template is hardcoded that could instead live here — that's the entire reason the file exists.

Built-in objects actually referenced in this chart

Discrepancy worth flagging .Chart is technically available in every template's context too — Helm always injects it, populated from Chart.yaml (.Chart.Name would resolve to order-platform, .Chart.Version to 0.1.0). But none of the four templates in this chart actually reference it — not once, checked directly against the files. It's often listed as one of the "core" built-ins in generic Helm tutorials, but this specific chart simply has no use for it: there's nothing in these manifests that needs to know the chart's own name or version.

Go text/template syntax this chart actually uses

  • {{ ... }} — substitution. {{ $name }}, {{ $svc.port }}, {{ $.Release.Namespace }}.
  • {{- range $name, $svc := .Values.services }} ... {{- end }} — iterates a map, covered fully in §4.
  • {{- if $svc.dbSecret }} ... {{- end }} — conditionally includes a block, covered in §5.
  • {{ $.Values.common.springProfile | quote }} — the quote pipe function, wrapping the value in double quotes in the output (k8s → "k8s"), from configmap.yaml.

The {{- / -}} whitespace-trim dashes — what they actually trim, and why

A leading {{- trims all whitespace immediately before the tag, back to and including the preceding newline. A trailing -}} does the same for whatever follows. Every control-flow tag in this chart's templates — every range, if, and end — opens with {{-.

The reason is mechanical: each of those tags sits on its own source line for readability, but a range/if/end line carries no actual YAML content of its own — it's pure control flow. Without the leading -, the newline at the end of that source line would still be emitted into the output, because Go's template engine treats everything outside {{ }} — including that trailing newline — as literal text to copy through verbatim. Trim it, and the control-flow line leaves no trace at all in the rendered result.

Not just cosmetic here Two of this chart's conditionals — {{- if $svc.dbSecret }} and {{- if $svc.healthProbe }} in deployment.yaml — sit inside a block sequence (the envFrom: list) and a block mapping respectively. An untrimmed blank line landing at the wrong indentation inside a block sequence is exactly the class of thing that produces genuinely invalid YAML, not just extra whitespace — the same failure mode investigated earlier in this project when a linter reported "invalid child element in a block sequence" against this exact file. The trim dashes here aren't a style preference; they're what keeps the false-branch output valid.

2. When rendering actually happens

Stated plainly, because it's easy to get backwards: template rendering — every range, every {{ }} substitution, every if — happens entirely on the machine running helm template, helm install, or helm upgrade, before anything is sent to the Kubernetes API server. It is a local, client-side text-substitution pass over the files in helm/order-platform/. It is not something that happens "at runtime" inside a running Pod, and it has nothing to do with the cluster's own scheduling or execution machinery.

The output of that render step — captured in full in §5 and §6 — is plain, ordinary Kubernetes YAML with zero Helm syntax remaining in it. No {{ }}, no range, no if. kubectl and the API server never see a template at all — only the fully-resolved manifest, indistinguishable from something a human typed by hand. A running container has no idea Helm exists; it just reads environment variables that came from a ConfigMap, the same as it would if that ConfigMap had been applied with a plain kubectl apply -f.

    healthProbe: false
    waitFor:

        port: 9092
      - host: order-elasticsearch

FieldWhy it exists — what breaks without it
imageAll four services build to genuinely different image names (Phase 7's own per-module Dockerfiles). No single hardcoded value could ever be correct for more than one service — this has to come from data.
portConsumed six separate times across the three templates (containerPort, both Service ports, both probe ports). The four services listen on genuinely different ports — 8080/8081/8082/8083, set in each service's own application.yml back in Phase 6 — so a shared template with this hardcoded would simply be wrong for three of the four services.
dbSecretThe one field allowed to be empty ("" for search-indexer-service) rather than always populated — that emptiness is exactly what the {{- if $svc.dbSecret }} conditional tests. search-indexer-service never had a Postgres dependency, so there's no credential to reference; without this field being data-driven, every service would need either a fabricated secretRef pointing at a Secret that doesn't exist (breaking that Pod's startup) or the template couldn't be shared across all four at all.
healthProbeA plain boolean, false only for search-indexer-service — because that service was never given the Actuator dependency, so it has no /actuator/health to probe. A probe hardcoded unconditionally into the template would misconfigure that one Deployment to poll an endpoint returning 404, and Kubernetes would never mark that Pod ready — a real failure, not a cosmetic one.
waitForA list, not a scalar — different length per service (2 entries for order-service/search-indexer-service, 3 for inventory-service/payment-service) and different content. This is what forces a range nested inside the outer range (see §6) — no fixed number of hardcoded lines could express "a different count of dependency checks per service."

4. The range mechanism, annotated

All three of configmap.yaml, service.yaml, and deployment.yaml open with the identical line:

{{- range $name, $svc := .Values.services }}

Go's text/template package sorts a map's keys before ranging over it — a deliberate, documented behavior, specifically so that template output is deterministic and reproducible across runs rather than following Go's own maps, whose iteration order is intentionally randomized at the language level. This isn't just asserted here — it's directly confirmed by the actual helm template output captured for this doc: every one of ConfigMap, Service, and Deployment renders in the same order — inventory-service, order-service, payment-service, search-indexer-service — alphabetical, not the order the entries happen to appear in values.yaml (which is order-service first).

Verified, not assumed Ran helm template order-platform helm/order-platform -n order-platform directly against this chart. The four rendered ConfigMaps appear in exactly that alphabetical order in the real output — confirming the sort-by-key behavior rather than taking it on faith.

$name binds to the current iteration's map key (a string — "order-service", etc.); $svc binds to that key's value — the nested image/port/dbSecret/healthProbe/waitFor settings for that one service.

deployment.yaml's full loop body, annotated

helm/order-platform/templates/deployment.yaml

envFrom: - configMapRef: name: {{ $name }}-config {{- if $svc.dbSecret }} - secretRef: name: {{ $svc.dbSecret }} {{- end }}configMapRef is unconditional — every service gets one. secretRef only renders if $svc.dbSecret is non-empty. Fully worked in §5.

--- {{- end }}--- is the YAML document separator — needed because this one template file produces multiple independent Deployment documents, one per loop iteration, all concatenated into a single rendered output. {{- end }} closes the outer range.

The net effect: one ~55-line template body, executed four times with four different $name/$svc bindings, produces four completely independent Deployment objects — verified directly in the next two sections.

5. Worked example: search-indexer-service

search-indexer-service is the one service that actually exercises both conditionals — no database, no health endpoint. Its exact values.yaml entry:

  search-indexer-service:
    image: order-service-search-indexer-service:latest
    port: 8083
    dbSecret: ""
    healthProbe: false
    waitFor:
      - host: order-kafka
        port: 9092
      - host: order-elasticsearch
        port: 9200

And its actual, complete rendered Deployment — real helm template output, not reconstructed by hand:

helm template order-platform helm/order-platform -n order-platform — search-indexer-service Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: search-indexer-service
  namespace: order-platform
spec:
  replicas: 1
  selector:
    matchLabels:
      app: search-indexer-service
  template:
    metadata:
      labels:
        app: search-indexer-service
    spec:
      initContainers:
        - name: wait-for-deps
          image: busybox:1.36
          command:
            - sh
            - -c
            - |
              until nc -z order-kafka 9092; do echo waiting for order-kafka; sleep 2; done
              until nc -z order-elasticsearch 9200; do echo waiting for order-elasticsearch; sleep 2; done
      containers:
        - name: search-indexer-service
          image: order-service-search-indexer-service:latest
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8083
          envFrom:
            - configMapRef:
                name: search-indexer-service-config
What's missing, and why No secretRef under envFrom — dbSecret: "" is falsy in Go templates, so {{- if $svc.dbSecret }}...{{- end }} evaluated false and the whole block vanished, cleanly, with no stray blank line (the trim dashes from §1 at work). No readinessProbe or livenessProbe at all — healthProbe: false, same mechanism. The container spec simply ends after envFrom.

Contrast with order-service's rendered Deployment — same template, same loop body, different $svc values, both conditionals true:

helm template order-platform helm/order-platform -n order-platform — order-service Deployment

kind: Deployment
metadata:
  name: order-service
  namespace: order-platform
spec:
  replicas: 1
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      initContainers:
        - name: wait-for-deps
          image: busybox:1.36
          command:
            - sh
            - -c
            - |
              until nc -z order-postgres 5432; do echo waiting for order-postgres; sleep 2; done
              until nc -z order-redis 6379; do echo waiting for order-redis; sleep 2; done
      containers:
        - name: order-service
          image: order-service-order-service:latest

          ports:
            - containerPort: 8080

                name: order-service-config
            - secretRef:
                name: order-service-db-credentials
          readinessProbe:
            httpGet:
              path: /actuator/health
              port: 8080

            periodSeconds: 5
          livenessProbe:

              path: /actuator/health
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10

Same template file, same 55 lines of source — two structurally different Kubernetes objects, purely because the data fed into $svc differed. That's the entire mechanism this chart relies on.

6. Worked example: inventory-service's waitFor, traced end to end

1. The exact source data

helm/order-platform/values.yaml, inventory-service entry
    waitFor:
      - host: inventory-postgres
        port: 5432
      - host: order-redis
        port: 6379
      - host: order-kafka
        port: 9092

2. The exact template lines that consume it

helm/order-platform/templates/deployment.yaml
          command:
            - sh
            - -c
            - |
              {{- range $svc.waitFor }}
              until nc -z {{ .host }} {{ .port }}; do echo waiting for {{ .host }}; sleep 2; done
              {{- end }}

A precise, easy-to-miss detail: inside this inner range $svc.waitFor, the dot (.) rebinds to each individual list item — not to $svc. That's why .host/.port work without needing to write $svc again inside the loop. This only works cleanly because the outer range used named variables (range $name, $svc := .Values.services) instead of touching the dot-context — so the outer loop's data stays reachable as $svc throughout, while the inner loop is free to rebind . to whatever it's iterating without losing anything.

3. The exact resulting lines in rendered output

helm template order-platform helm/order-platform -n order-platform — inventory-service Deployment, command block
              until nc -z inventory-postgres 5432; do echo waiting for inventory-postgres; sleep 2; done
              until nc -z order-redis 6379; do echo waiting for order-redis; sleep 2; done
              until nc -z order-kafka 9092; do echo waiting for order-kafka; sleep 2; done

Three list entries in values.yaml → three until nc -z ... lines in the rendered shell script, one inner-loop iteration each. Nothing invented — this is the literal, unedited relevant slice of the real render captured for this document.

8. Why this design, and its real cost

This project has a direct, lived comparison available, not a hypothetical one: the individual hand-rolled k8s/order-service-deployment.yaml, k8s/inventory-service-deployment.yaml, k8s/payment-service-deployment.yaml, and k8s/search-indexer-service-deployment.yaml files (plus their four matching *-configmap.yaml files) still exist in this repository — now marked SUPERSEDED, but still readable. That's four separate ~50–60 line files that were, before this chart existed, close to 90% identical boilerplate: same apiVersion/kind structure, same selector/label pattern, same envFrom/probe shape — differing only in the handful of fields this chart's services map now isolates.

The DRY win is real: a future change to, say, the probe path or imagePullPolicy is one edit to deployment.yaml instead of four (soon more, as services are added) individually-maintained files that have to be kept consistent by hand. Adding a fifth service means adding one entry to values.yaml, not writing three new template files.

The cost is equally real, and worth stating plainly rather than glossing over: the actual shape of any one service's Deployment is no longer visible by reading a single flat file. To know whether search-indexer-service gets a secretRef or a livenessProbe, you have to mentally execute the template against its specific values.yaml entry — read the range, evaluate the ifs, understand what the whitespace-trim dashes do to the output — exactly the exercise §5 and §6 walked through by hand. A hand-rolled per-service file never asks that of a reader; everything about that one Deployment is right there, linearly, top to bottom. This chart trades that immediacy for not repeating yourself four times over — a genuine trade-off between two real costs, not a strictly-better replacement for the files it superseded.
